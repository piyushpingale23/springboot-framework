# Idempotency Pattern

## 1. Definition

The Idempotency Pattern ensures that performing the same operation multiple times produces the same business effect as performing it once.

It is especially important when clients retry requests due to network failures or timeouts.

**Example:** If a payment request is submitted three times with the same idempotency key, the customer should be charged only once.

## 2. Why Do We Need It?

Imagine a client sends a payment request.

```text
Client
   |
   | Payment request: ₹1,000
   v
Payment Service
   |
   v
Payment successful
   |
   X Response lost due to network failure
```

The client does not receive the response and retries the request.

Without idempotency, the customer might be charged twice.

With idempotency, the service recognizes the duplicate request and returns the original result instead of processing another payment.

## 3. Idempotency Key

An idempotency key is a unique identifier generated by the client for a logical operation.

Example:

```http
POST /payments
Idempotency-Key: payment-order-101
Content-Type: application/json
```

```json
{
  "orderId": 101,
  "amount": 1000
}
```

If the client retries the same payment, it must reuse the same key.

- First request: Process the payment and store the result.
- Duplicate request: Find the existing operation and return its stored result.
- New payment: Use a new idempotency key.

**Important:** Reusing the same key with a different request payload should be rejected.

## 4. How It Works

```text
Client sends request with idempotency key
                  |
                  v
        Check stored idempotency key
                  |
          +-------+-------+
          |               |
       Exists          Not found
          |               |
          v               v
   Return saved result  Process payment
                          |
                          v
                    Store result
                          |
                          v
                    Return response
```

## 5. Spring Boot Implementation Example

### Step 1: Create an Entity

Store the idempotency key and the result associated with it.

```java
@Entity
@Table(
    name = "idempotency_records",
    uniqueConstraints = @UniqueConstraint(
        columnNames = "idempotency_key"
    )
)
public class IdempotencyRecord {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "idempotency_key", nullable = false)
    private String idempotencyKey;

    private String status;
    private String response;

    // Getters and setters
}
```

The unique constraint prevents multiple records from being created for the same key.

### Step 2: Create a Repository

```java
public interface IdempotencyRepository
        extends JpaRepository<IdempotencyRecord, Long> {

    Optional<IdempotencyRecord> findByIdempotencyKey(
            String idempotencyKey);
}
```

### Step 3: Implement the Basic Logic

```java
@Service
public class PaymentService {

    private final IdempotencyRepository repository;

    public PaymentService(IdempotencyRepository repository) {
        this.repository = repository;
    }

    public String processPayment(String key) {

        Optional<IdempotencyRecord> existing =
                repository.findByIdempotencyKey(key);

        if (existing.isPresent()) {
            return existing.get().getResponse();
        }

        // Illustrative only: replace with actual payment processing.
        String result = "Payment successful";

        IdempotencyRecord record = new IdempotencyRecord();
        record.setIdempotencyKey(key);
        record.setStatus("COMPLETED");
        record.setResponse(result);

        repository.save(record);

        return result;
    }
}
```

This demonstrates the basic concept, but **it is not sufficient for production payments**. Concurrent duplicate requests can both pass the initial lookup before either saves the record.

A production implementation needs atomic key claiming, appropriate transaction handling, request-payload validation, and a defined approach to in-progress or failed operations. External payment-provider calls also need their own idempotency support or reconciliation strategy.

## 6. Exactly-Once Business Effect

In distributed systems, guaranteeing that a request is delivered or executed exactly once across every component is difficult.

A practical approach is to allow retries while ensuring that duplicate requests do not produce duplicate business effects.

For example:

```text
Same payment request delivered 3 times
                  |
                  v
          Idempotency protection
                  |
                  v
       Only 1 successful charge
```

This is commonly described as achieving an **exactly-once business effect** through idempotency, deduplication, and appropriate transaction boundaries.

It does not necessarily mean the request was executed only once internally.

## 7. Where Is Idempotency Used?

- Payment APIs
- Order creation APIs
- Money transfers
- Booking and reservation systems
- Message consumers processing duplicate events
- Retried requests in distributed systems

## 8. Key Point

**Idempotency makes retries safe by ensuring that the same logical request does not create duplicate business effects. Use a unique idempotency key and enforce its uniqueness atomically.**
